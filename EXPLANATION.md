## 1. В чем главная суть Лабораторной работы №3?

В прошлых двух лабах мы проектировали систему «на бумаге»:
* **В ЛР1** придумали таблицы базы данных (товары, склады, ячейки, остатки) и нарисовали диаграммы C4.
* **В ЛР2** составили список команд API (`openapi.yaml` / Swagger), как фронтенд будет общаться с сервером.

**В ЛР3 мы наконец пишем реальный работающий код серверного приложения!**
Но вместо того чтобы свалить весь код в один огромный файл `index.js` (файлопомойку), мы строим **взрослую многослойную архитектуру (Clean / Layered Architecture)**:
1. Раскладываем код по изолированным папкам-слоям.
2. Прячем настройки и секреты в файл `.env`, чтобы они не утекли на GitHub.
3. Запускаем сервер и делаем первый живой эндпоинт **`GET /api/v1/health`** (проверка здоровья сервера).

## 2. Разбор структуры папок (почему всё так разложено)

Преподаватель обязательно спросит: *«Покажи структуру проекта и объясни, зачем тебе столько папок?»*

Вот наша структура каталогов:

```text
3/
├── cmd/
│   └── main.ts                   # Точка входа в приложение (Main)
├── internal/                     # Внутренний код (скрыт от внешнего мира)
│   ├── config/
│   │   └── config.ts             # Загрузка настроек из .env
│   ├── controller/
│   │   └── health.controller.ts  # Слой API (ловит HTTP-запросы)
│   ├── service/
│   │   └── health.service.ts     # Слой бизнес-логики (чистые правила)
│   └── repository/
│       └── health.repository.ts  # Слой БД (работа с базой данных)
├── .env.example                  # Шаблон настроек (лежит в Git)
├── .env                          # Твои секреты (скрыт в .gitignore)
├── .gitignore                    # Список файлов, которые Git игнорирует
├── package.json                  # Список библиотек и скрипты npm run
└── tsconfig.json                 # Настройки компилятора TypeScript
```

### Как идет запрос от клиента (Аналогия с рестораном):
1. **Клиент (Браузер / Телефон)** отправляет запрос `GET /api/v1/health`.
2. **`cmd/main.ts`** — это фундамент здания ресторана: запускает сервер и соединяет всех работников.
3. **`internal/controller/` (Официант):** ловит входящий HTTP-запрос, считывает заголовки, зовет Повара (`service`), а когда Повар отдает готовое блюдо — упаковывает его в красивый JSON со статусом `200 OK`.
4. **`internal/service/` (Шеф-повар / Бизнес-логика):** готовит данные. Он вообще не знает, кто такой HTTP, что такое JSON или куки. Он просто берет данные из конфига и спрашивает у Кладовщика (`repository`), жива ли база данных.
5. **`internal/repository/` (Кладовщик базы данных):** ходит в PostgreSQL за данными. В этой лабе здесь заглушка (Mock), которая говорит: *«Да, база доступна»*. В 5-й и 6-й лабе тут будут реальные SQL-запросы.
6. **`internal/config/` (Бухгалтерия / Снабжение):** считывает порт сервера и имя проекта из файла `.env`.

## 3. Переменные окружения: `.env` против `.env.example`

### Почему файл `.env` никогда нельзя пушить в Git?
В `.env` хранятся пароли к базе данных, ключи шифрования JWT и приватные токены. Если залить их на GitHub:
1. Роботы-сканеры находят секреты в открытых репозиториях за 1–2 минуты.
2. Злоумышленники получают доступ к базе данных и удаляют или воруют данные.
3. Поэтому файл `.env` всегда прописан в `.gitignore`.

### Зачем тогда нужен `.env.example`?
Другой программист или препод, когда клонирует твой репозиторий, не увидит `.env`.
Он открывает `.env.example`, видит список всех нужных настроек (`APP_NAME`, `HTTP_PORT`), копирует его командой:
```bash
cp .env.example .env
```
и спокойно запускает приложение.

## 4. Что такое Health Check и зачем он нужен?

Эндпоинт **`GET /api/v1/health`** возвращает:
```json
{
  "status": "pass",
  "app_name": "WMS Inventory Management API",
  "version": "1.0.0",
  "environment": "development"
}
```

### Зачем он в реальной жизни?
В микросервисах крутятся сотни серверов под управлением **Kubernetes** или **Docker**.
Человек не может ежесекундно проверять каждый сервер руками.
Вместо этого автоматический мониторинг раз в 5 секунд шлет запрос на `/health`:
* Если ответ `200 OK` со статусом `pass` — сервис живой, на него можно слать запросы клиентов.
* Если сервис завис или отвечает ошибкой `500` — Kubernetes мгновенно убивает зависший контейнер и поднимает новый.

## 5. Что такое Dependency Inversion (Инверсия зависимостей)?

Это буква **D** из принципов **SOLID**.

* **Как было бы плохо:** Если бы Контроллер внутри себя жестко писал `const service = new HealthService()`. Тогда Контроллер намертво привязан к конкретному классу.
* **Как сделано у нас (правильно):**
  * Мы создали интерфейс `IHealthService`.
  * Контроллер принимает сервис через конструктор (`constructor(service: IHealthService)`). Это называется **Dependency Injection (внедрение зависимостей)**.
  * А связываем мы их в одном месте — в `cmd/main.ts`.
  * **Что это дает:** Мы можем в любой момент написать фальшивый тестовый сервис `MockHealthService` и протестировать Контроллер за 1 миллисекунду без поднятия реальных серверов.

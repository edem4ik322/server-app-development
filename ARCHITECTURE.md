**Дисциплина:** Разработка серверных приложений

**Вариант №12:** Система учета складских запасов (*Inventory Management*)  

---

## 1. Описание предметной области

Проект представляет собой серверную часть системы управления складом (WMS). 

**Ключевые возможности системы:**
* **Адресное хранение:** каждый товар хранится на определенном складе и привязан к конкретной ячейке (`bin_location`).
* **Контроль остатков:** запрет списания больше фактического остатка (защита от отрицательного баланса).
* **Журналирование операций:** фиксация всех типов движений (приемка, списание, перемещение между ячейками/складами, инвентаризация).
* **Мониторинг дефицита:** автоматическое выявление позиций с остатком ниже минимального порога (`min_stock_level`) для своевременного заказа поставщикам.

---

## 2. Роли пользователей и сценарии использования (Use Cases)

В системе выделены три роли с разграничением прав:
1. **Кладовщик (`STOREKEEPER`):** проводит физические операции с товаром (приемка от поставщиков, комплектация и списание заказов, перемещение по ячейкам, корректировка по результатам инвентаризации).
2. **Аналитик закупок (`PROCUREMENT_ANALYST`):** отслеживает остатки, настраивает минимальные пороги запасов и работает со списком дефицитных позиций (алертов).
3. **Администратор (`ADMIN`):** регистрирует сотрудников, управляет справочником складов и номенклатурой товаров.

## 4. Спецификация REST API (REST API Specs)

### 4.1. Принципы проектирования REST API

При разработке контракта API соблюдаются стандарты REST:
1. **Существительные во множественном числе для ресурсов:** URI указывает на сущность, а не на действие (например, `POST /products`, а не `/createProduct`).
2. **HTTP-методы отражают действие:**
   * `GET` — безопасное чтение ресурса или коллекции;
   * `POST` — создание нового ресурса или проведение транзакции;
   * `PATCH` — частичное обновление полей сущности;
   * `DELETE` — удаление ресурса.
3. **Использование стандартных статус-кодов HTTP** для явного разделения успехов и классов ошибок (клиентские `4xx`, серверные `5xx`).
4. **Единый формат данных:** все запросы и ответы передаются в формате `application/json` с кодировкой UTF-8.

### 4.2. Сводная таблица REST-эндпоинтов

| Метод | URI | Описание | Доступ (Роль) | Ожидаемый код |
| :--- | :--- | :--- | :--- | :--- |
| **POST** | `/api/v1/auth/login` | Аутентификация сотрудника по логину и паролю, выдача JWT | Публичный (Все) | `200 OK` / `401 Unauthorized` |
| **GET** | `/api/v1/products` | Получение списка товаров с пагинацией и поиском | Все авторизованные | `200 OK` |
| **POST** | `/api/v1/products` | Добавление новой номенклатурной позиции в каталог | Администратор (`ADMIN`) | `201 Created` / `409 Conflict` (дубль SKU) |
| **PATCH** | `/api/v1/products/{id}/threshold` | Изменение минимального порога остатка товара | Аналитик закупок, Администратор | `200 OK` / `400 Bad Request` |
| **GET** | `/api/v1/warehouses/{warehouse_id}/stock` | Просмотр остатков и ячеек хранения на складе | Кладовщик, Аналитик, Администратор | `200 OK` / `404 Not Found` |
| **DELETE** | `/api/v1/warehouses/{id}` | Удаление склада из системы | Администратор (`ADMIN`) | `204 No Content` / `409 Conflict` (есть остатки) |
| **POST** | `/api/v1/stock/transactions` | Проведение движения (приемка, списание, перемещение) | Кладовщик (`STOREKEEPER`) | `201 Created` / `409 Conflict` (списание в минус) |
| **GET** | `/api/v1/alerts/low-stock` | Список товаров с остатком ниже минимального лимита | Аналитик закупок, Администратор | `200 OK` |

### 4.3. Применяемые статус-коды HTTP

* **`200 OK`** — успешный запрос на чтение (`GET`) или частичное обновление (`PATCH`), а также успешная авторизация (`POST /auth/login`).
* **`201 Created`** — ресурс успешно создан в базе данных (`POST /products`, `POST /stock/transactions`).
* **`204 No Content`** — ресурс успешно удален (`DELETE /warehouses/{id}`), тело ответа пустое.
* **`400 Bad Request`** — ошибка валидации входных данных (например, отрицательное число в поле `min_stock_level` или некорректный UUID).
* **`401 Unauthorized`** — клиент не предоставил токен или передан недействительный/истекший JWT.
* **`403 Forbidden`** — пользователь аутентифицирован, но его роль не имеет прав на это действие (например, кладовщик пытается создать склад).
* **`404 Not Found`** — запрашиваемый ресурс по указанному ID не существует в базе.
* **`409 Conflict`** — конфликт бизнес-правил или состояния базы (попытка списать товар в минус, повторный артикул SKU или удаление склада с товаром).
* **`500 Internal Server Error`** — непредвиденная внутренняя ошибка сервера.

---

### 4.4. Единый формат ошибок (`ErrorResponse`)

Все ошибочные ответы API стандартизированы и возвращаются в едином формате JSON:

```json
{
  "code": "INSUFFICIENT_STOCK",
  "message": "Недостаточно товара на складе для выполнения списания",
  "timestamp": "2026-10-07T22:30:00Z",
  "details": [
    "Текущий остаток: 3 шт.",
    "Запрошено к списанию: 10 шт."
  ]
}
```

* `code` — машиночитаемый строковый код ошибки для клиентского приложения (удобно обрабатывать в коде).
* `message` — понятное человеку описание проблемы на русском языке.
* `timestamp` — время возникновения ошибки по стандарту ISO 8601.
* `details` — массив конкретных деталей или ошибок валидации полей (опционально).

Спецификация API полностью описана в файле [openapi.yaml](./openapi.yaml) по стандарту OpenAPI 3.0.3.

## 5. Ответы на контрольные вопросы

### Вопрос 1: В чем разница между передачей параметров через Query (`?limit=10`), Path (`/users/{id}`) и Request Body? Каковы правила выбора каждого способа?

**Ответ:**
* **Path-параметры (`/warehouses/{warehouse_id}/stock`):**
  * *Что это:* часть пути URI.
  * *Когда использовать:* когда параметр однозначно идентифицирует конкретный ресурс или родительскую сущность в иерархии (обычно это первичный ключ `ID` или `UUID`). Без этого параметра запрос теряет смысл.
* **Query-параметры (`/products?category_id=...&limit=20&page=1`):**
  * *Что это:* параметры после знака `?`, разделенные `&`.
  * *Когда использовать:* для опциональных модификаций выборки — фильтрации, пагинации, сортировки и поиска. Ресурс остается тем же самым каталогом, но клиент уточняет критерии выдачи.
* **Request Body (Тело запроса в JSON):**
  * *Что это:* полезная нагрузка внутри HTTP-запроса (`POST`, `PUT`, `PATCH`).
  * *Когда использовать:* при передаче сложных, структурированных или конфиденциальных данных (создание товара с множеством полей, передача пароля при логине). В URL такие данные передавать нельзя из-за ограничений на длину URL, отсутствия типизации и риска утечки данных через логи серверов.

### Вопрос 2: Что такое идемпотентность HTTP-методов? Почему GET, PUT и DELETE считают идемпотентными, а POST — нет?

**Ответ:**
* **Идемпотентность** — это свойство HTTP-метода, означающее, что повторный вызов одного и того же запроса с теми же параметрами приводит к **точно такому же состоянию сервера**, как и однократный вызов (побочный эффект не накапливается).
* **GET идемпотентен (и безопасен):** чтение данных вообще не изменяет состояние сервера. Сколько бы раз мы ни запросили `GET /products`, база данных не изменится.
* **PUT идемпотентен:** метод выполняет полную замену ресурса. Если отправить `PUT /products/{id}` с новыми данными 1 раз или 10 раз подряд, ресурс в базе примет указанное состояние и больше меняться не будет.
* **DELETE идемпотентен:** первое удаление удалит запись из базы. Повторные вызовы `DELETE /warehouses/{id}` либо вернут 404, либо ничего не изменят — ресурса на сервере уже нет, итоговое состояние системы одинаково.
* **POST НЕ идемпотентен:** метод предназначен для добавления новых записей или выполнения транзакций. Если отправить `POST /stock/transactions` (приемка 10 шт.) три раза подряд, на склад трижды поступит товар (всего +30 шт.) и в базе создадутся три разные записи транзакций. Каждый вызов меняет состояние сервера заново.

### Вопрос 3: В каких ситуациях сервер должен возвращать код 401 Unauthorized, а в каких — 403 Forbidden?

**Ответ:**
* **`401 Unauthorized` (Ошибка аутентификации — "Кто ты?"):**
  * Сервер возвращает 401, когда клиент **не подтвердил свою личность**.
  * *Примеры:* заголовок `Authorization` отсутствует вовсе, передан поврежденный JWT-токен, токен просрочен, либо при входе введен неверный пароль. Решение: клиенту нужно пройти аутентификацию (залогиниться).
* **`403 Forbidden` (Ошибка авторизации — "Я знаю кто ты, но тебе сюда нельзя"):**
  * Сервер возвращает 403, когда личность клиента установлена, но у него **недостаточно прав доступа** к запрашиваемому действию.
  * *Примеры:* кладовщик успешно залогинился и прислал валидный токен, но пытается вызвать метод создания товара `POST /products`, доступный только роли `ADMIN`. Сервер понимает, кто делает запрос, но отклоняет его из-за политик безопасности. Повторный логин с теми же данными здесь не поможет.

### Вопрос 4: Зачем в OpenAPI-спецификации используется блок `components/schemas` и ключевое слово `$ref`?

**Ответ:**
Блок `components/schemas` и директива `$ref` используются для реализации принципа **DRY (Don't Repeat Yourself)** при описании API:
1. **Переиспользование моделей данных:** вместо того чтобы вручную дублировать структуру товара или пользователя в каждом эндпоинте (в списках, создании, редактировании), модель описывается один раз в `components/schemas/ProductResponse` и затем подключается ссылкой: `$ref: '#/components/schemas/ProductResponse'`.
2. **Единая точка изменений:** если у сущности меняется тип поля или добавляется новое свойство, достаточно отредактировать схему в одном месте, и она автоматически обновится во всех эндпоинтах.
3. **Стандартизация ошибок:** единый формат ошибок `ErrorResponse` подключается во всех HTTP-статусах `400`, `401`, `403`, `404`, `409` через `$ref`, исключая разнобой в форматах ответов.
4. **Читаемость файла:** спецификация остается компактной и структурированной, разделяя маршрутизацию (`paths`) и типы данных (`schemas`).

### Вопрос 5: В чем разница между HTTP-методами PUT и PATCH при обновлении ресурсов в REST API?

**Ответ:**
Разница заключается в **объеме и логике обновления данных**:
* **`PUT` (Полная замена ресурса):**
  * Клиент обязан передать в теле запроса **все обязательные поля** ресурса целиком.
  * Если какое-то поле не передано в теле `PUT`-запроса, сервер, согласно спецификации, обязан затереть его значение (установить в `null` или значение по умолчанию). Это эквивалентно полной перезаписи документа.
* **`PATCH` (Частичное обновление ресурса):**
  * Клиент передает **только те поля, которые требуется изменить**. Все остальные поля остаются нетронутыми.
  * *Пример из нашего склада:* в эндпоинте `PATCH /api/v1/products/{id}/threshold` аналитик передает только новое значение `{"min_stock_level": 15}`. При этом название товара, его SKU, единица измерения и категория не перезаписываются и не требуют повторной отправки клиентом. Это экономит трафик и предотвращает случайное затирание соседних данных.

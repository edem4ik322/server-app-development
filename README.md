## 📂 Структура проекта (Layered / Clean Architecture)

Проект строго разделен на независимые слои в соответствии с принципом разделения ответственности (*Separation of Concerns*):

```text
3/
├── cmd/                          # Точка входа в приложение
│   └── main.ts                   # Bootstrap: сборка слоев (Dependency Injection) и запуск сервера
├── internal/                     # Внутренний код серверного приложения
│   ├── config/                   # Слой конфигурации
│   │   └── config.ts             # Загрузка и типизация переменных окружения (.env)
│   ├── controller/               # API / Transport Layer (Слой представления)
│   │   └── health.controller.ts  # Обработка HTTP-запросов и формирование ответов
│   ├── service/                  # Domain / Business Logic Layer (Слой бизнес-логики)
│   │   └── health.service.ts     # Чистая логика проверки состояния сервиса
│   └── repository/               # Data Access Layer (Слой работы с данными)
│       └── health.repository.ts  # Интерфейс доступа к хранилищу (подготовка к БД в ЛР5)
├── diagrams/                     # Архитектурные схемы из ЛР1 (C4 Containers, ERD)
├── .env.example                  # Шаблон переменных окружения для репозитория
├── .gitignore                    # Исключения Git (.env, node_modules, dist)
├── ARCHITECTURE.md               # Архитектурный отчет из ЛР1
├── openapi.yaml                  # Спецификация REST API (OpenAPI 3.0.3) из ЛР2
├── package.json                  # Манифест зависимостей и скрипты запуска
├── tsconfig.json                 # Конфигурация компилятора TypeScript
└── README.md                     # Документация проекта
```

## 🚀 Установка и запуск

### 1. Установка зависимостей
```bash
npm install
```

### 2. Настройка переменных окружения
Создайте локальный файл `.env` на основе шаблона `.env.example`:
```bash
cp .env.example .env
```

Параметры в `.env`:
* `APP_NAME` — наименование сервиса (`"WMS Inventory Management API"`);
* `APP_ENV` — тип окружения (`development`, `production`, `test`);
* `APP_VERSION` — версия приложения (`1.0.0`);
* `HTTP_PORT` — порт веб-сервера (`8080`).

> ⚠️ **Важно:** файл `.env` добавлен в `.gitignore` и никогда не попадет в репозиторий.

### 3. Запуск приложения

* **Режим разработки (с автоматическим перезапуском при изменениях):**
  ```bash
  npm run dev
  ```

* **Сборка и продакшн-запуск:**
  ```bash
  npm run build
  npm start
  ```

## 🎓 Ответы на контрольные вопросы для защиты

### 1. Почему слой бизнес-логики (Service Layer) не должен знать о деталях HTTP-запросов (структуре JSON, заголовках, req/res)?
* **Причина:** Принцип разделения ответственности (*Single Responsibility Principle*).
* Если сервис будет завязан на объекты Express `Request` и `Response`, мы не сможем повторно использовать ту же самую бизнес-логику для CLI-утилит, брокеров сообщений (RabbitMQ/Kafka) или gRPC-вызовов.
* Кроме того, логику без зависимости от HTTP в разы проще покрывать модульными тестами (*Unit Tests*), передавая простые параметры и проверяя возвращаемый результат.

### 2. В чем опасности хранения секретов (пароли к БД, API-ключи, JWT-секреты) непосредственно в исходном коде программы?
* **Утечка данных:** Если код попадет в публичный или корпоративный Git-репозиторий (GitHub/GitLab), любой пользователь или бот со сканером секретов мгновенно получит доступ к базе данных и инфраструктуре.
* **Невозможность гибкой смены окружения:** Для локальной разработки, тестового стенда (Staging) и боевого сервера (Production) нужны разные пароли и адреса БД. Зашитые в код значения требуют перекомпиляции и пересборки проекта при каждом изменении секрета.
* **История Git помнит всё:** Даже если удалить пароль в следующем коммите, он навсегда останется в истории коммитов репозитория.

### 3. Зачем нужен файл `.env.example`, если сам файл `.env` находится в `.gitignore`?
* Файл `.env.example` служит **живой спецификацией и документацией** по всем необходимым переменным окружения для других разработчиков и DevOps-инженеров.
* Новый разработчик, клонируя репозиторий, не видит `.env` (так как тот скрыт правилами `.gitignore`), но по `.env.example` точно знает, какие ключи и с какими типами данных требуются для старта приложения.

### 4. Для чего в микросервисной и серверной архитектуре используется эндпоинт Health Check (`/health`)?
* **Оркестраторы контейнеров (Kubernetes, Docker Swarm):** используют Liveness и Readiness пробы. Если сервис завис или упал, оркестратор видит ошибку на `/health` и автоматически перезапускает упавший контейнер, либо снимает с него трафик.
* **Балансировщики нагрузки (Nginx, Traefik, AWS ALB):** опрашивают эндпоинт, чтобы направлять запросы клиентов только на живые и готовые к работе инстансы сервиса.
* **Системы мониторинга (Prometheus, Grafana, Uptime Kuma):** оповещают дежурных инженеров при сбоях сервиса.

### 5. Что такое инверсия зависимостей (Dependency Inversion) и как она помогает связывать между собой слои API, сервисов и репозиториев?
* **Суть принципа (буква D в SOLID):**
  1. Модули верхних уровней не должны зависеть от модулей нижних уровней. И те, и другие должны зависеть от **абстракций (интерфейсов)**.
  2. Абстракции не должны зависеть от деталей. Детали должны зависеть от абстракций.
* **Как реализовано у нас:**
  * `HealthController` зависит не от конкретного класса `HealthService`, а от интерфейса `IHealthService`.
  * `HealthService` зависит не от конкретного класса репозитория, а от интерфейса `IHealthRepository`.
  * Экземпляры классов передаются через конструктор (**Dependency Injection**).
  * **Плюсы:** мы можем легко подменить реальный репозиторий БД на Mock-объект в тестах, не меняя ни единой строчки бизнес-логики.
